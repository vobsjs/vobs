# AGENTS.md — Working in the **vobs framework repository**

> This file is for humans and AI **developing vobs itself**.
> The contract for application projects (business apps built with vobs) is generated by
> `vobs agent-doc` — not this one.
>
> Every rule below comes from **real rework**, not imagined standards. The cost of violating
> each one is given in parentheses.

## 1. Check whether it already exists before building (the most expensive rule)

**Measured: the same failure pattern happened 4 times within one cycle.**

| What to look up | How |
|---|---|
| **Checks / scripts the repo already has** | **`pnpm run checks`** ← run this first |
| Symbols / APIs exported by the framework | `vobs api <keyword>` |
| Diagnostic-code rules and the correct way to write them | `vobs explain <code>` |

- ❌ Once: wrote an equivalent of `check-imports` from scratch, **and on top of a wrong
  conclusion added `workspace:*` to 3 bundle-style packages**, which would have turned their
  assertions red (cost: wasted work + 3 packages broken + one round of rollback)
- ❌ Once: re-implemented `inferStateDebugName` (it already existed and was more correct)
- ✅ **Before writing a new script/check, read the header comment of a similar file** —
  those few lines are exactly what would have stopped me

## 2. When you say "verified", state **which channel** it was verified on

The channels are separate and cover different rules:

| Channel | Covers |
|---|---|
| `pnpm run check:source` | Static analysis + compiler diagnostics (whole repo) |
| `vite build` / `dev` | Compiler diagnostics + analyzer diagnostics |
| Runtime guardrails (`@vobs/vobs/dev`) | `C210` / `C211` (judged against the **real dependency set**, the most precise) |
| `pnpm run check:runtime` | Runs the above in a real Chrome |

- ❌ Once: ran `check:source`, saw "0 errors", and declared "C108 has zero false positives repo-wide" —
  but at the time `vobs check` **did not run the compiler at all**, so that rule **was never executed
  once**. That "verification" was empty.
- ✅ Before a new rule ships, at minimum run: **repo-wide `check:source`** (watch for false positives) +
  **the `ai-mistakes` corpus** + **`guide-verification`** (if it ships fix text)

## 3. Measure first, then assert

- ❌ Once: inferred "static `C210` may false-positive" and prepared to downgrade it — without ever having measured
- ✅ Later: built 7 adversarial shapes, **measured exactly 1 real false positive** (same-name local
  shadowing), and only then did the downgrade have grounds
- ❌ Once: inferred that `(unnamed signal)` meant "the `.ts` file was not compiled" — measurement showed
  it was a **barrel re-export**
- ✅ **Inference may propose hypotheses, but must not be written into commit messages or docs as conclusions**

## 4. False positives destroy trust; **silent mistakes** are worse than no change

- ❌ `VOBS_C104` used to be an `error`; in a real project it hit **18 spots, 16 of them false positives** —
  the cost was the whole team starting to ignore warnings
- ✅ When unsure, always go **warning**; **leave the real hard gate to the runtime guardrails**
  (they judge against the real dependency set)
- ✅ For a new rule, **run the real repo-wide check first** to look for false positives, then decide severity

## 5. A diagnostic's fix text **is also code**

- ❌ The first version of `C108`'s fix said "write it at the usage site" — in practice that **only holds
  for JSX child positions**; turning the component's top-level `return` into a ternary converts a crash into
  "**the UI never switches**" (more deceptive)
- ❌ `C104`'s fix recommended `class={cond ? 'is-on' : 'is-off'}`,
  but real projects only have compound selectors — following it produced "the class is added but the
  style does not apply"
- ✅ **Every fix suggestion must come with a test proving "rewriting per the suggestion produces zero
  diagnostics"** (see `guide-verification.test.ts`)

## 6. Document known limitations; do not hide them

- ✅ `docs/silent-failures.md` lists the error shapes that are **currently silent**, each with "**why it is
  not done**" (otherwise it looks like an oversight)
- ✅ `vobs explain` **explicitly says so** for a code with no entry, and lists the codes it does cover —
  **no inventing**
- ❌ Guessed documentation is worse than no documentation

## 7. Mechanical discipline for editing files (lessons already paid for)

- **`.mjs` is JS**: writing `const x: string[] = []` is an **immediate syntax error and the change silently
  does nothing** (stepped on 3 times; `pnpm run check:scripts` now catches it)
- **Do not edit source with regexes of questionable idempotency**: a non-greedy `[\s\S]*?` once jumped across
  two import statements and corrupted a file, and a `findIndex` once matched a same-named prefix (C211's fix)
  and deleted 50 lines. **Use line-number-based, line-by-line asserted replacement instead**, and
  **`git checkout` first so you can roll back**
- **Package names and directory names do not always match**: `dsh-plugin-vobs` lives in `packages/dsh-plugin`.
  Grepping with the package name as the path **silently returns nothing**
- **If you change a workspace package's exports, run `pnpm run build:packages` first** —
  the CLI imports from `dist/`; otherwise it fails in an unreadable form like `node:internal/modules/run_main`
- **If you touch dependencies of any `packages/*/package.json` (including reverting them!), you must sync the
  lockfile and verify with `--frozen-lockfile`**

  ❌ Incident: acting on a wrong conclusion, I added `@vobs/dsh`/`@vobs/vobs` to 3 dsh plugin packages and ran
  `pnpm install` (the lockfile updated accordingly), then rolled back the `package.json` files with
  `git checkout` — **but committed the lockfile that still carried those two dependencies** (`6a2e8cc`).
  CI went red on `pnpm install --frozen-lockfile` from then on:

  ```
  ERR_PNPM_OUTDATED_LOCKFILE  pnpm-lock.yaml is not up to date with packages/dsh-console/package.json
    * 2 dependencies were removed: @vobs/dsh@workspace:*, @vobs/vobs@workspace:*
  ```

  **Why it was never caught locally**: the gate and `verify:packages` both use the **existing `node_modules`**
  and never reinstall → **lockfile drift is structurally undetectable**. Only `--frozen-lockfile` catches
  this class of problem.

  ✅ Remedy and check: `pnpm install --no-frozen-lockfile` → check that `git diff pnpm-lock.yaml` contains
  **only** the intended differences → `pnpm install --frozen-lockfile` must pass → then commit

## 8. Commits and releases

- Commit messages in English — explain why (including pitfalls), not just what
- **Layered changelog and commits** (2026-10-28): `CHANGELOG.md` carries only **user-perceivable** changes
  (new capabilities / what got fixed / which diagnostic code changed behavior / upgrade notes); semantic-fix
  entries only reference the diagnostic code (details live in `vobs explain <code>` — do not duplicate them);
  internal details (silent-failures consolidation, binding-analysis implementation, corpus/verification process)
  belong in the **body of the semantic-fix commit** — do not create maintainer log files. Commits come in two
  layers: routine changes get a one-line title; semantic fixes / diagnostic changes / breaking changes get the
  full decision record (behavior before, measured evidence, why this direction was chosen), with the body
  anchoring diagnostic codes via `Refs: VOBS_Cxxx`
- Before committing, run `pwsh -NoProfile -File .artifacts/gate.ps1` (test:run + typecheck +
  check:scripts + check:source; judge by the **exit code**, not by counting output)
- Releases follow `docs/npm-release.md`; **tags are validation-only, publishing is manual** (a decision, not a transition)
- **Do not loosen the criteria to make things "look finished"** — when unsure, write it into `docs/silent-failures.md`
