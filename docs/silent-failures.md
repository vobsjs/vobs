# 静默失败清单（编译期合法、运行期错）

> 这份清单回答一个问题：**还有哪些 AI 常犯的错误，框架抓不住？**
>
> 每一条都带「为什么不做的原因」—— 否则它看起来像忘了。
> 可执行的版本在 `packages/compiler/src/ai-mistakes.test.ts`：那里的
> `caughtBy: null` 条目就是这个文件的机器可读副本，覆盖率会打印出来。

## 为什么要维护这份清单

这一轮里「诊断存在但某条通道不可见」出现了**三次**，全是人肉发现的。
而"**根本不存在诊断**"是更贵的一类：编译通过、类型通过、运行期偶发错。

静默失败对 AI 写的代码尤其致命 —— 模型不会停下来自查，它只会继续写下一段。

## 静默的两条

### 1. 数组原地修改不触发更新

```ts
const list = state([1])
list.value.push(2)          // 引用没变 → 信号不通知
return <div>{list.value.length}</div>
```

**React 里这也是错的**（要 `setList([...list, 2])`），但 React 的表层直觉是
"改完靠重新渲染生效"，所以模型仍然常写。

**为什么不做诊断**：需要**作用域/绑定分析** —— 确认 `list` 确实绑定到
`state(...)`。没有它，对普通数组的 `.push()` 也会报，而那是完全正常的代码。
现有分析器没有绑定解析（`analyzeSource` 只按名字匹配）。

**缓解**：`vobs explain VOBS_C118` 等条目里反复强调"数组更新必须换引用"；
`ai-mistakes` 语料把它记下来，等有了绑定分析再补。

### 2. 组件体内提前 `return null` 做守卫

```ts
function P() {
  if (loading.value) return null     // 挂载时固化 —— 之后永不切换
  return <div>done</div>
}
```

**为什么不做诊断（这是有意不做的，不是漏了）**：

同一个形态在**渲染辅助函数**里是**正确代码**：

```ts
function renderRow(item: Item) {
  if (empty.value) return null        // 每次求值都重跑 → 完全正常
  return <tr>…</tr>
}
```

要区分这两者必须知道「**这个函数是不是组件**」—— 而静态分析决定不了
（`vobs` 的组件就是普通函数）。加了这条规则会把大量正确的渲染辅助函数报成错误。

**这与 `VOBS_C104`/`C107` 的处理一致**：那两条只报"返回值里含 JSX 且读了信号"的形态，
已经是能静态判定范围内最准的边界。**宁可漏，不可误** —— C104 那次的教训是
18 处命中 16 处误报，代价是整个团队开始无视告警。

## 已从"静默"转为"有诊断"的（本轮的进展）

| 形态 | 现在 |

## 判定标准（下次有人要加规则时按这个）

一条静态规则够不够格进框架，看三点：

1. **能不能静态判定**（判不了就别加 —— 见上面第 2 条）
2. **误报代价**：`error` 会让正确代码的 CI 失败，那是不可接受的；
   所以拿不准的一律 `warning`，而**真正的硬门禁交给运行时护栏**
   （它按真实依赖集判定，跨函数精确）
3. **有没有验证**：新规则必须① 跑全仓真实检查看误报，② 进
   `ai-mistakes` 语料，③ 若给 fix 文案则进 `guide-verification`
   （**按建议改写后必须零诊断**）

第 3 条是这一轮用返工换来的：C108 的 fix 文案改了两轮，
第一版会把用户从"崩"引到"界面不切换"（更隐蔽）。
